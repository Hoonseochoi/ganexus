### GA Calendar 성능 최적화 가이드 (배포 환경 기준)

배포 환경에서 **날짜/월 전환 시 반응 속도가 느려지는 원인 후보**와, **우선 적용하면 효과가 큰 최적화 방법**을 정리했습니다.  
가능하면 아래 순서대로 적용하는 것을 권장합니다.

---

### 1. 서버 데이터 패칭 / DB 쿼리 최적화

- **원인 후보**
  - 매월/날짜 전환마다 `/api/schedules` 등을 새로 호출하면서, **지점별 전체 기간 조회**를 반복.
  - `listSchedulesForBranch` 쿼리가 `from / to` 범위 없이 전체를 가져오거나, 인덱스가 적절하지 않으면 **쿼리 시간이 길어짐**.
  - Neon의 **scale-to-zero / cold start** 로 인해, 첫 쿼리마다 수백 ms 이상 추가 지연이 발생.

- **개선 방법**
  - **쿼리 범위 제한**
    - `from`, `to` 를 **해당 월 ±1주 정도**로 제한해서 가져오기.
    - 예: `from = firstDayOfMonth - 7일`, `to = lastDayOfMonth + 7일`.
  - **인덱스 점검**
    - `schedules` 테이블에 아래 인덱스 고려:
      - `(branch_name, start_at)`, `(branch_name, end_at)` 복합 인덱스
      - `WHERE is_soft_deleted = false` 조회가 많다면 `PARTIAL INDEX` 도 검토:
        - 예: `CREATE INDEX ... ON schedules(branch_name, start_at) WHERE is_soft_deleted = false;`
  - **Neon 콜드 스타트 완화**
    - **커넥션 풀링 엔드포인트(-pooler)** 를 사용하는지 확인.
    - 주기적으로 적당한 간격으로 **헬스 체크 쿼리**를 보내 cold start 빈도를 줄이는 방법도 고려.

### 2. 서버 컴포넌트 렌더링 최소화 (Next.js 16 App Router)

- **원인 후보**
  - 월/날짜 이동 시 마다 **서버 컴포넌트(캘린더 전체 페이지)** 를 통으로 다시 렌더링.
  - 서버 렌더링 + 데이터 패칭까지 합쳐져 **체감 지연**이 크게 느껴질 수 있음.

- **개선 방법**
  - **서버 컴포넌트: “월 단위 데이터만 제공”**
    - `app/page.tsx` 에서는:
      - 현재 년/월 + 주변 범위의 일정 배열만 생성해서 **프롭 형태로 내려만 주기**.
      - 캘린더 셀 계산 로직은 그대로 두되, 서버에서 불필요한 추가 가공(정렬/필터링 중복)을 줄이기.
  - **클라이언트 컴포넌트로 월/날짜 전환 처리**
    - 월/날짜 전환에 **서버 네비게이션(router.push)** 를 사용 중이라면:
      - 가능하면 **클라이언트 상태(useState)** 로 전환하고, 서버는 초기 데이터만 내려주도록 변경.
    - “한 번 내려받은 월 데이터”는 클라이언트에서 **메모리 캐시** 해 두고, 다시 같은 월을 볼 때 서버 요청을 생략.

---

### 3. 클라이언트 렌더링 비용 줄이기 (React 렌더 최적화)

- **원인 후보**
  - 월 단위로 수십~수백 개 일정이 있고, 날짜 클릭/월 변경 시 **전체 캘린더 그리드 + 우측 패널 컴포넌트가 다시 렌더링**.
  - `map` 으로 렌더하는 컴포넌트가 크고, `props` 체인이 깊어 **리렌더가 비싸다**.

- **개선 방법**
  - **메모이제이션**
    - 일정 리스트/캘린더 셀 계산은 `useMemo` 로 감싸고, 의존성 배열을 명확히 설정.
    - 일정 카드/셀 컴포넌트는 `React.memo` 로 감싸서, **실제 데이터가 바뀐 셀만 리렌더**.
  - **파생 데이터(예: todaySchedules, eventsByDateStr) 메모**
    - `eventsByDay`, `eventsByDateStr`, `schedulesForSelected` 계산은 `useMemo` 로 묶어서,
      월/날짜가 바뀔 때만 다시 계산되도록 제한.
  - **불필요한 프롭 변경 줄이기**
    - 스타일 클래스, 핸들러 함수는 `useCallback` 으로 안정화해서,  
      자식 컴포넌트가 “프롭 변경” 때문에 리렌더 되지 않도록 조절.

### 4. 네트워크 레이어 최적화 (API 및 캐싱)

- **원인 후보**
  - 날짜/월 전환마다 **항상 새로 fetch** 하여, 이미 본 구간도 재요청.
  - 브라우저 캐시/Next 캐시를 활용하지 않고, **모든 요청을 no-store** 로 보내는 경우.

- **개선 방법**
  - **TanStack Query 도입 검토**
    - 일정 데이터를 **키 단위로 캐싱** 하고, 월/날짜가 바뀌어도 이미 받아온 범위라면 재요청 없이 메모리에서 읽기.
    - 백그라운드 리패치로 최신 상태 유지.
  - **HTTP 캐시 헤더 활용**
    - 변경 빈도가 낮은 보조 데이터(예: 공지사항, 브랜치 정보)는 `Cache-Control` 을 통해 **재사용**.
    - 일정 데이터도 **짧은 max-age(수 초~수십 초)** 를 줘도 UX 상 문제 없으면 캐싱.

### 5. UI/UX 측면의 체감 속도 개선

- **원인 후보**
  - 실제 서버/네트워크 시간이 짧아도, **로딩 상태 표현이 없거나, 레이아웃 점프가 심하면** 느리게 느껴짐.

- **개선 방법**
  - **네비게이션 로딩 상태**
    - 월/날짜 전환 버튼 클릭 시 짧은 로딩 상태(버튼 비활성화, opacity 감소, “로딩…” 텍스트)를 보여주어, 사용자가 “입력이 먹혔다”고 즉시 느끼게 합니다.
  - **낙관적 UI / 스켈레톤**
    - 이미 캐시된 일정 리스트를 우선 보여주고, 백그라운드에서 새 데이터를 가져와 교체하거나,
      일부 영역에 스켈레톤을 짧게 노출해 체감 속도를 개선할 수 있습니다.
  - **애니메이션 최적화**
    - 월 전환 애니메이션이 있다면, CSS transform 기반(translate/opacity)으로 구현하고,
      리플로우를 유발하는 속성 변경은 피하기.

### 6. 모니터링 및 계측

- **왜 필요한가**
  - 어디에서 시간이 가장 많이 쓰이는지(쿼리 vs 서버 렌더 vs 클라이언트 렌더 vs 네트워크)를 알아야,
    최적화 우선순위를 정확히 정할 수 있음.

- **추천 방법**
  - **Next.js / 브라우저 측 측정**
    - `performance.mark`, `performance.measure` 등을 사용해
      “월 버튼 클릭 → 화면 안정화까지” 구간을 계측하고, 브라우저 콘솔이나 전용 로깅 엔드포인트로 전송합니다.
  - **DB 쿼리 시간 로깅**
    - `query` 래퍼에서 시작/종료 시간을 찍고, 일정 범위(from/to)별로 느린 쿼리를 로그로 분리해 Neon 대시보드와 함께 분석합니다.
  - **Neon 대시보드**
    - 쿼리 타임, 커넥션 수, cold start 패턴을 확인해서,
      필요한 경우 인덱스/플랜/브랜치 구성을 재검토.

---

### 7. 우선순위 요약

1. **DB 쿼리 범위 및 인덱스 최적화** (from/to + 인덱스)
2. **월/날짜 전환 시 서버 네비게이션 최소화, 클라이언트 상태 기반 전환**
3. **캘린더/일정 리스트 컴포넌트 메모이제이션 (useMemo, React.memo, useCallback)**
4. **TanStack Query 같은 클라이언트 캐싱 도입**
5. **스켈레톤/낙관적 UI로 체감 속도 개선**
6. **쿼리/렌더 타임 계측으로 병목 지점 파악**

위 단계들을 순서대로 적용하면, 배포 환경에서 **월/날짜 이동 시 체감 반응 속도**를 눈에 띄게 개선할 수 있습니다.
