## 2025-03 초기 설계

### ORM 미사용 결정
- **결정**: Prisma, Drizzle 등 ORM 도입 안 함. `pg` 직접 사용.
- **이유**: 프로젝트 규모가 작고, SQL을 직접 제어하는 게 Neon 환경에서 더 예측 가능함. ORM 마이그레이션 복잡도 불필요.
- **트레이드오프**: 타입 안전성은 직접 관리해야 함.

### Supabase Auth 미사용 결정
- **결정**: 자체 인증 구현 유지.
- **이유**: 초기 설계 당시 Supabase에서 Neon으로 전환. Auth도 자체 구현으로 통일.
- **트레이드오프**: OAuth, 소셜 로그인 추가 시 직접 구현 필요.

### 3패널 고정 레이아웃
- **결정**: 좌/중앙/우 3패널 구조 고정.
- **이유**: 지점 관리 특성상 캘린더(중앙) + 멤버(좌) + 상세(우) 조합이 최적.
- **트레이드오프**: 모바일에서는 MobileCalendarShell로 별도 처리.

### 역할 체계 (admin/manager/agent)
- **결정**: 3단계 역할 + is_approved 플래그 조합.
- **이유**: 초대코드 → 승인 대기 플로우가 핵심 UX. role만으로는 승인 상태 표현 불가.
- **구현**: middleware.ts에서 role + is_approved 조합으로 리다이렉트 처리.
